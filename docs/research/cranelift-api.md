# Research digest: cranelift api

_Verified August 2026 via parallel web research. Raw JSON: docs/research/raw/_

## Summary

As of August 2026 the active cranelift crate series is 0.135.0 (published 2026-08-20 alongside the latest wasmtime train), with 0.133.x/0.134.x still receiving patches and several older parallel lines (0.111.x, 0.123.x) maintained for older wasmtime LTS branches; all cranelift-* crates must be pinned to the same minor. The canonical JIT flow for the current version is: settings::builder -> cranelift_native::builder().finish(flags) -> JITBuilder::with_isa(isa, default_libcall_names()) -> JITModule::new(builder) -> declare_function/define_function -> finalize_definitions() (now returns ModuleResult<()>, the old FinalizedDefinitions guard is gone) -> get_finalized_function(FuncId) -> transmute to extern "C" fn. On Windows x64 use CallConv::WindowsFastcall (= CallConv::triple_default for the windows triple; matches Rust extern "C"), which cranelift-jit handles correctly including shadow space and RtlAddFunctionTable unwind registration. Two recent API breaks matter for HELIX Lite: MemFlags was redesigned (~wasmtime 36, early 2026) from bitflags into a handle over MemFlagsData with builder methods (notrap()/aligned()/readonly()/trusted()), and JITModule::hotswap/set_definition was removed entirely (v25 cycle), so never rely on hot-patching.

## Key facts

1. Current versions (crates.io API, checked 2026-08): cranelift-jit and cranelift-object max_version 0.135.0 (published 2026-08-20); actively patched lines 0.134.4/0.134.3, 0.133.3, 0.123.14, 0.111.13. docs.rs 'latest' currently resolves to 0.134.3 for cranelift-jit/module/object/codegen/frontend/native. Pin ALL cranelift-* crates (cranelift, cranelift-codegen, cranelift-frontend, cranelift-module, cranelift-jit, cranelift-native, cranelift-object) to one identical minor — they share ir::* types.
2. Canonical minimal JIT example (verified against bytecodealliance/wasmtime main, cranelift/jit/examples/jit-minimal.rs): set flags use_colocated_libcalls=false and is_pic=false (FIXME says keep false until x64 supports it); isa_builder = cranelift_native::builder().unwrap_or_else(...); isa = isa_builder.finish(settings::Flags::new(flag_builder)); let mut module = JITModule::new(JITBuilder::with_isa(isa, cranelift_module::default_libcall_names())); signatures via module.make_signature(); declare_function(name, Linkage::Local, &sig); build bodies with FunctionBuilder/FunctionBuilderContext, bcx.finalize(module.target_config()); module.define_function(id, &mut ctx); module.clear_context(&mut ctx); module.finalize_definitions().unwrap(); let code = module.get_finalized_function(id); unsafe { mem::transmute::<_, extern "C" fn() -> u32>(code) }().
3. API changes to know: JITModule::finalize_definitions now has signature pub fn finalize_definitions(&mut self) -> ModuleResult<()> — older tutorials showing a returned FinalizedDefinitions lifetime-guard are outdated. JITBuilder constructors: new(libcall_names: Box<dyn Fn(LibCall)->String + Send + Sync>) -> ModuleResult<Self>, with_flags(flags: &[(&str,&str)], libcall_names), with_isa(isa: OwnedTargetIsa, libcall_names) -> Self. cranelift_native::new_host_isa() is gone; current functions are builder() / builder_with_options() / infer_native_flags() returning an IsaBuilder you .finish(flags) yourself.
4. Host symbol exposure: JITBuilder::symbol<K: Into<String>>(&mut self, name, ptr: *const u8) -> &mut Self, symbols(iter) for batches (later definitions override earlier), and symbol_lookup_fn(Box<dyn Fn(&str) -> Option<*const u8> + Send>) for dynamic resolution with platform fallback when the internal table misses. There is no SymbolLookupFn type on the current JITBuilder page (older releases had type SymbolLookupFn = Arc<dyn Fn(&str) -> Option<*const u8> + Send + Sync>); the callback shape is Fn(&str) -> Option<*const u8>. Resolution model: FuncId = a function (declare_function(..., Linkage::Import, &sig) creates a named import that resolves via the symbol table at finalize; declare_anonymous_function exists too); DataId = data objects (declare_data(name, linkage, writable, tls), define_data(DataId, &DataDescription)) — use DataId for read-only constant pools/literals, FuncId+symbol registration for host runtime functions. Cross-references: module.declare_func_in_func(func_id, &mut bcx.func) -> FuncRef for direct JIT->JIT calls; module.declare_data_in_func(data, &mut func) -> GlobalValue for globals.
5. Calling conventions (docs.rs cranelift-codegen 0.134.3 isa::CallConv): variants Fast, Tail, SystemV, WindowsFastcall ('Windows fastcall convention, also used for x64 and ARM'), AppleAarch64, Probestack, Winch, PreserveAll. Methods triple_default(triple: &Triple) -> Self (x86_64+Windows => WindowsFastcall, else SystemV) and for_libcall(flags, default_call_conv). On Windows x64 windows_fastcall passes first 4 int/ptr args in RCX,RDX,R8,R9 with 32-byte shadow space; Rust's extern "C" on x86_64-pc-windows-msvc is exactly this ABI, so declare all HELIX signatures with call_conv CallConv::WindowsFastcall (or triple_default) and transmute get_finalized_function results to extern "C" fn. Do NOT use SystemV signatures on Windows — mismatched register assignment (>4 args go to rdi/rsi/...) is silent corruption. cranelift-jit itself handles the convention correctly (wasmtime ships it on Windows); libcalls get for_libcall convention automatically.
6. Memory ops (InstBuilder, 0.134.3): fn load<T1: Into<MemFlagsData>, T2: Into<Offset32>>(self, Mem: Type, MemFlags: T1, p: Value, Offset: T2) -> Value; store<T1,T2>(self, MemFlags: T1, x: Value, p: Value, Offset: T2) -> Inst. Address operand must be pointer-width integer (I64 on x64) — extend loop indices with uextend/sextend I32->I64 before address math. Scaled indexing has no dedicated CLIF instruction: compute iadd(base, imul(idx_wide, 8)) or fold constant strides into the Offset32 immediate; the x64 backend's addressing-mode matching folds shift+add into base+index*scale memory operands. CLIF text form: v1 = load.i64 notrap aligned readonly v0+16.
7. MemFlags redesign (breaking, landed ~wasmtime 36, Jan-Feb 2026, PR bytecodealliance/wasmtime#10842): MemFlags is no longer a bitflags u8/u16; it is documented as an opaque entity index referring to a MemFlagsData stored in a MemFlagsSet inside the DataFlowGraph. Flag semantics survive as typed accessor/builder methods on MemFlagsData (trusted(), notrap(), aligned(), readonly, endianness little/big, checked for sandboxing); migration pattern MemFlags::new().with_notrap().with_aligned() -> builder style (...notrap().aligned()). Because InstBuilder::load/store take Into<MemFlagsData>, frontend code constructs MemFlagsData values; verify exact constructor spelling against cranelift/codegen/src/ir/memflags.rs for your pinned version.
8. Recommended MemFlags for HELIX heap arrays: notrap + aligned for element accesses into Vec/malloc-backed storage (you control alignment; set aligned only when the access size divides the element alignment), add readonly ONLY for provably-immutable memory (enables GVN/LICM hoisting safety), leave endianness default (little), do not use trusted() unless you can prove no trapping/aliasing surprises, checked is for sandbox schemes and unnecessary here.
9. Loop-body callback into host parallel_for: mark the body function a normal Local function in the same JITModule with WindowsFastcall sig (e.g. param [I64 iteration_index]); register the host runtime once: builder.symbol("helix_parallel_for", helix_parallel_for as *const u8) where Rust side is extern "C" fn(start: i64, end: i64, body: extern "C" fn(i64)) (or *const u8 body if you prefer casting on the host side); declare the import with declare_function("helix_parallel_for", Linkage::Import, &sig) and call it via declare_func_in_func. Obtain the raw body address only AFTER finalize_definitions(): let body_ptr: *const u8 = module.get_finalized_function(body_id). Simplest robust pattern: skip embedding the pointer in JIT code — after finalize, drive the parallel_for call from Rust, passing body_ptr cast to the extern "C" fn type. Ordering caveats: pointers are invalid until finalize_definitions succeeds, stay valid while the JITModule lives, and become invalid after unsafe module.free_memory(); hotswap/set_definition no longer exists (removed in wasmtime v25 cycle, PR #8670), so recompilation means building a fresh JITModule.
10. cranelift-object status (0.134/0.135): ObjectBuilder::new<V: Into<Vec<u8>>>(isa, name, libcall_names) -> ModuleResult<Self> (no relocation-model parameter anymore), with toggles per_function_section(bool), per_data_object_section(bool), unwind_info(bool) — on Windows it emits .pdata/.xdata-style SEH info rather than DWARF .eh_frame; Mach-O eh_frame is not implemented, ELF+COFF work. ObjectModule implements Module; ObjectModule::finish() -> ObjectProduct; ObjectProduct { pub object: object::write::Object<'static>, functions/data_objects SecondaryMaps } with function_symbol(FuncId), data_symbol(DataId), and emit(self) -> Result<Vec<u8>, Error> (consumes self; write bytes with std::fs::write). The object crate is re-exported so versions stay in sync. COFF format is chosen from the ISA's target triple, so configure the isa/triple as x86_64-pc-windows-msvc.
11. COFF/link.exe workflow and friction: emit app.obj then link.exe /OUT:app.exe app.obj /SUBSYSTEM:CONSOLE with a CRT (libcmt.lib static, or ucrt.lib+msvcrt.lib); unresolved externals like __acrt_iob_func mean missing CRT/legacy_stdio_definitions.lib; you must supply a proper entry (mainCRTStartup calling your exported main, or /ENTRY for freestanding). No COMDAT, no debug-info emission; libcalls (memcpy/memset/ceilf32...) must resolve at link time unless you registered them yourself. lld-link (rust-lld ships with the Rust toolchain) is a drop-in linker that removes the Visual Studio Build Tools dependency. This path is viable for a HELIX 'compile to .exe' demo but is strictly more setup than the JIT path.
12. Windows/JIT runtime facts: x64 Windows enforces DEP always; cranelift-jit allocates code memory and flips protection (VirtualProtect PAGE_READWRITE -> PAGE_EXECUTE_READ-style transitions) — works out of the box on stock Windows 11. Arbitrary Code Guard (ACG) / strict CFG process mitigations break any JIT: if the compiler exe opts into ACG via SetProcessDisallowedMsiAndScript.../process mitigation policy or manifest, executable-page creation fails at runtime — leave them off. Unwind info on x64 Windows is mandatory for anything that unwinds or backtraces through JIT frames; cranelift emits SEH .pdata/.xdata and cranelift-jit registers it with the OS (RtlAddFunctionTable lineage, PR #4785 era fixes); historical bugs were wrong image base and unsorted/partial RUNTIME_FUNCTION entries — fixed in current lines, but keep JIT invocations panic-free (wrap the transmuted call in catch_unwind in the HOST so unwinding never crosses JIT frames; Rust panics escaping into JIT code without intact unwind info crash in ntdll!RtlUnwindEx).
13. Other practicalities: settings flags worth setting — opt_level=speed/none, use_colocated_libcalls=false and is_pic=false (both recommended false in the official example for x64 today); probestack/enable_heapstack not needed for a course project. Context reuse pattern: module.make_context()/clear_context() and make_signature()/clear_signature() exist precisely to recycle allocations across many small functions — relevant when you JIT dozens of loop-body kernels. BranchProtection enum and JITMemoryProvider trait (SystemMemoryProvider vs ArenaMemoryProvider) are exposed by cranelift-jit 0.134 for branch-protection-targeted hosts and bulk-reserved memory, but defaults are fine.

## Recommendations

1. Pin the whole cranelift stack to one line — cranelift = "0.135", cranelift-jit = "0.135", cranelift-object = "0.135", etc. (or the fully patched 0.134.x if a transitive dep forces it) — and never mix minors; types from cranelift-codegen::ir flow through every crate.
2. Copy cranelift/jit/examples/jit-minimal.rs from the wasptime repo as your skeleton: settings::builder() with use_colocated_libcalls=false + is_pic=false, cranelift_native::builder().finish(flags), JITModule::new(JITBuilder::with_isa(isa, default_libcall_names())), declare/define/finalize_definitions/get_finalized_function/transmute. Ignore blog posts showing JITBuilder::new() with no args or a FinalizedDefinitions guard — they predate the current API.
3. Use CallConv::WindowsFastcall explicitly for every HELIX signature (params, imports, libcalls inherit via for_libcall), and type all host-facing functions in Rust as extern "C". Never emit SystemV-convention functions on Windows.
4. Expose the parallel runtime with builder.symbol(...) registrations made once at JITBuilder construction (print, alloc_array, helix_parallel_for, reduction helpers), then declare_function(..., Linkage::Import, &sig) per module. Keep a single registry table mapping HELIX intrinsic name -> (symbol string, Signature) so codegen stays declarative.
5. For array element access: keep array base as an I64 value, widen 32-bit indices with uexpand/uextend to I64, compute iadd(base, imul(idx, elem_size)) (elem_size 4/8 for f32/i32 and f64/i64), and load with ins().load(types::F64, flags_notrap_aligned, addr, 0). Add readonly only to loads LICM proved invariant-safe.
6. Drive parallel_for from the HOST side: after finalize_definitions(), grab the loop-body pointer via get_finalized_function and invoke your own thread pool from Rust. This avoids embedding finalized addresses as iconst literals in JIT code and eliminates finalize-order hazards; reserve the JIT-calls-parallel_for-with-iconst-pointer pattern for the demo slide where you want the IR to look self-contained.
7. Wrap every host->JIT call site in std::panic::catch_unwind(AssertUnwindSafe(...)) and treat JIT frames as no-unwind territory; verify once on your machine that a Rust backtrace captured inside a JIT frame resolves (proves unwind registration works on your Windows 11 box).
8. Do the standalone-.exe stretch goal with cranelift-object + rust-lld (lld-link) rather than requiring full MSVC Build Tools: ObjectBuilder::new(isa_msvc_triple, "helix", default_libcall_names()).unwind_info(true), finish()->ObjectProduct, emit()->Vec<u8>, fs::write to .obj, then link with CRT libs; budget time for CRT/entry-symbol friction and consider emitting a C-main stub instead of /ENTRY hacks.
9. Write a tiny smoke test early that JITs 'fn f(x: f64) -> f64 { x * 2.0 }' and compares against native eval on all 32 logical CPUs under load — it will catch calling-convention, MemFlags-API, and unwind-registration problems in minutes instead of during the parallelization milestone.
10. Check docs.rs for YOUR pinned version before coding against MemFlags: the bitflags->MemFlagsData refactor changed construction syntax in early 2026; confirm the exact builder methods (notrap/aligned/readonly/trusted) from the memflags.rs source of that release.

## Pitfalls

1. Stale tutorials abound: JITBuilder::new() without libcall_names, cranelift_native::new_host_isa(), finalize_definitions returning a FinalizedDefinitions guard, and hotswap/set_definition all no longer exist or changed. Anything dated before ~mid-2025 is suspect; diff against the jit-minimal.rs example on wasmtime main instead.
2. Mixing cranelift-* crate minors fails to compile (ir::Function/Signature type mismatches) with confusing errors — lockstep-pin everything.
3. Using SystemV call_conv on Windows produces code that reads args from rdi/rsi/rcx... while callers pass in rcx/rdx/r8/r9: with <=4 scalar args it may appear to WORK by luck (rcx/rdx coincide) and then corrupt silently at 5+ args or with floats mixed in. Always WindowsFastcall.
4. MemFlags::new().with_aligned() style code from pre-2026 examples will not compile after the MemFlags/MemFlagsData refactor (~wasmtime 36); conversely guessing the NEW builder-method names from memory risks errors — check memflags.rs for the exact pinned release.
5. get_finalized_function before finalize_definitions, keeping the pointer past module.free_memory(), or dropping the JITModule while worker threads still execute loop bodies = dangling executable memory. The module must outlive all in-flight parallel work.
6. Panics or C++-style unwinding crossing a JIT frame on Windows relies on RUNTIME_FUNCTION unwind metadata; an escape route through unregistered or mis-based code crashes deep in ntdll!RtlUnwindEx. Contain panics on the host side.
7. Enabling process mitigations (Arbitrary Code Guard, or strict CFG policies) for your compiler exe will make cranelift-jit fail to create executable pages at runtime — leave mitigations off for the JIT configuration; also note JIT code addresses are not valid CFG indirect-call targets if you ever compile the host with /guard:cf enforcement.
8. is_pic=true/use_colocated_libcalls=true are still flagged unsupported on x64 in the official example — keep them false or you get relocation failures in the JIT.
9. cranelift-object COFF path pitfalls: forgetting CRT libs gives unresolved __acrt_iob_func/__imp_* errors; libcalls (memcpy, fmodf, ceil) must come from somewhere; no debug info means debugger sessions show raw addresses; emit() consumes ObjectProduct so you cannot emit twice.
10. Load/store address operands MUST be pointer-width (I64): loading with an I32 address is a verifier error, and forgetting uextend on 32-bit loop indices is the single most common frontend bug.
11. readonly flag on mutable shared arrays lets the optimizer hoist loads out of loops whose iterations another thread mutates — with automatic parallelization this becomes a real data-race-as-optimizer-bug; only mark readonly for genuinely immutable data.
12. crates.io's 'newest_version' field (0.123.14) disagrees with 'max_version' (0.135.0) because old wasmtime-LTS lines still receive patch publishes; don't interpret 0.123.x as the current stable line.
