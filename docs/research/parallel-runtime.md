# Research digest: parallel runtime

_Verified August 2026 via parallel web research. Raw JSON: docs/research/raw/_

## Summary

For HELIX Lite's helix_parallel_for(start,end,body_fn_ptr,ctx,nthreads), the best teaching-value-plus-performance design is a two-stage runtime: v0 = std::thread::scope spawn-per-call with static contiguous chunks (trivially correct, makes fork/join cost measurable), upgraded to v1 = a persistent worker pool woken per parallel region with either static equal chunks (optimal for uniform memory-bound loops) or OpenMP-guided scheduling via one relaxed atomic fetch_add counter (chunk = remaining/nthreads, min-clamped). Reductions must use per-thread partials padded to their own 128-byte cell (crossbeam CachePadded convention) combined serially after join — never atomics in the hot loop and never unpadded accumulator arrays, which measurably cost 2–10x. Honest benchmark expectations on a dual-channel DDR5 desktop: saxpy-style kernels at 50M elements are capped by ~65–85 GB/s achievable DRAM bandwidth, giving roughly 4–6x speedup at 8–16 threads (parallel efficiency 25–60%), while cache-resident compute-bound kernels scale near-linearly (12–15x at 16 threads); report achieved GB/s versus measured STREAM-triad peak rather than raw "speedup".

## Key facts

1. std::thread::scope (stable since Rust 1.63, doc: doc.rust-lang.org/std/thread/fn.scope.html) auto-joins all spawned threads on scope exit and panics if an auto-joined thread panicked; it borrows non-'static data via the 'env lifetime. It adds ~zero overhead over raw spawn — the cost is N kernel thread creations plus one join barrier.
2. Thread spawn cost: Rust std::thread on Windows maps to CreateThread; measured spawn+join cycles are ~50–100 us per thread on Windows 11 versus ~20–35 us on Linux (Stack Overflow 'How expensive is it to spawn a thread in Rust', community 2024 benchmarks on Ryzen 7950X ~55–80 us). One real project measured std::thread::scope dispatch at ~0.4 ms total and switched to a warm pool; a criterion-based gist found std_thread_scope 'so abysmal for light loads it had to be removed from log-scale charts'.
3. Warm-pool dispatch cost is ~0.5–5 us (Win32 SubmitThreadpoolWork measurements) versus 20–300 us for CreateThread (Raymond Chen cites ~1M cycles including stack-commit page faults); break-even around 10–50 tasks. Fork/join/barrier cost for an already-assembled team is ~1–5 us per parallel region at 32 threads (Fastbar arXiv:2407.04561: pthread barrier 48 threads ~4.4 us, lock-free ~1.6 us; TaskFlow measures trivial parallel-for launch overhead ~2–10 us at 32 threads).
4. Intel OpenMP runtime spins by default KMP_BLOCKTIME=200 ms before sleeping workers (Intel oneAPI docs); OMP_WAIT_POLICY=ACTIVE/PASSIVE overrides; barrier arrival/departure sub-us while workers spin. This spin-then-block hybrid is the industry-standard idle policy and the model for HELIX's pool.
5. Guided self-scheduling (Polychronopoulos & Kuck 1987): chunk = remaining_iterations / nthreads clamped to a minimum, claimed via atomic fetch_add on a shared next-index counter; this is exactly how GCC libgomp (gomp_loop_guided_next in libgomp/loop.c: left = end - next; chunk = left / nthreads; floor to ws->chunk_size; __sync_fetch_and_add(&ws->next, chunk)) and LLVM libomp (kmp_dispatch.cpp) implement schedule(guided).
6. OpenMP schedule guidance (openmp.llvm.org, LLNL tutorial): static = best for uniform-cost and memory-bound loops (contiguous per-thread streams preserve hardware prefetching and page locality, zero runtime overhead); dynamic chunk=1 self-scheduling is commonly 1.5–3x slower than static on balanced loops purely from cacheline ping-pong on the counter plus broken prefetch streams; dynamic/guided with chunk 8–64 recovers 80–95% of static performance under moderate imbalance; guided beats plain dynamic by ~10–30% on irregular work.
7. Static partition formula (GCC libgomp iter.c, matches OpenMP spec option 2): q = n / nthreads; t = n % nthreads; thread i gets start = q*i + min(i,t), len = q + (i < t) — first t threads get one extra iteration; the spec forbids relying on the exact split.
8. False sharing: two threads writing distinct variables on the same 64-byte line force MESI invalidation traffic (~40–100+ cycles per transfer vs ~4 for an L1 hit). Measured magnitudes: Martin Thompson's classic Java demo ~450M ops/s unpadded vs ~1B+ padded (mechanical-sympathy.blogspot.com 2011); Preshing's increment benchmark ~1.2 ns/inc single-threaded vs ~12 ns/inc under 4-thread false sharing (~10x); Intel's 'Avoiding and Identifying False Sharing Among Threads': expected 4x speedup collapses to ~0.4–0.5x unpadded, padding restores ~3.8x; literature range 2–10x, up to 15x worst-case (Wikipedia/ACM studies).
9. Padding width: use 128 bytes, not 64. crossbeam_utils::CachePadded (v0.8.22, crates.io) pads to N=128 on x86-64/aarch64/powerpc64 because Intel spatial prefetchers pull pairs of 64-byte lines; Rust idiom is #[repr(align(128))] struct Cell(T). crossbeam-utils also ships Backoff (spin_loop -> yield_now -> exponential sleep to 10 ms) implementing the canonical bounded-spin idle strategy.
10. Reduction combine patterns: per-thread partials combined after the join beat atomics whenever update rate is high — Fedor Pikus (CppCon 2017) measured 10–50x slowdown for contended fetch_add vs thread-local accumulation; Herlihy & Shavit ch.12 formalizes combining trees (O(log P) depth) as the scalable alternative. For min/max there is no native x86 float atomic min/max, so atomics require CAS retry loops that degrade worse than fetch_add; per-thread min/max + final combine is strongly preferred. TBB parallel_reduce is built on exactly the private-accumulator + join pattern. OpenMP 5.x reduction clause: privatize per implicit task with monoid initializer (+ -> 0, * -> 1, min -> type MAX, max -> type MIN), combine at region end in an UNSPECIFIED order — the spec explicitly warns floating-point results are not bitwise-reproducible run-to-run.
11. Cost threshold heuristics: canonical OpenMP if-clause example is #pragma omp parallel for if(n > 10000) (LLNL tutorial); when if(false) the region executes serialized 'as if' num_threads(1) and nested regions serialize too (unlike num_threads(1)). Hager & Wellein (Introduction to HPC): each thread needs ~10^4–10^5 useful operations to amortize startup; for light vector loops break-even can be millions of iterations. Community consensus floor: >= 1000–10000 lightweight iterations per thread; compute-heavy bodies profit from tens per thread. Fork/join overhead ~1–10 us per region (U. Oregon CIS635 notes).
12. Bandwidth arithmetic for the demo (50M f32 elements): saxpy moves 12 B/element (read x 4 + read y 4 + write y 4) = 600 MB/pass; daxpy 24 B/el = 1.2 GB; f64 reduction reads 8 B/el = 400 MB. Dual-channel DDR5-5200 (7950X stock) achieves ~65–70 GB/s STREAM triad; DDR5-6000 tuned ~82–88 GB/s (Phoronix/TechPowerUp); dual-channel DDR4-3200 ~42–46 GB/s. So the saxpy wall-clock floor is ~0.6 GB / 70 GB/s ~= 8.6 ms regardless of thread count.
13. Measured saxpy scaling: single-threaded scalar saxpy reaches only ~8–12 GB/s (~30% of peak; Karl Rupp's vectorization study shows scalar ~30% vs AVX ~90%+ of peak), giving a theoretical ceiling near 6x; course/Stack Overflow reports at n=1e8 consistently show ~1.9x @2T, ~3.5x @4T, 5–6x @8T, then flat — parallel efficiency at 16 threads typically 25–40% for DRAM-streaming kernels. Cache-resident FMA-dense kernels show the contrast: 15.2–15.9x at 16 threads on the same machines (LBNL roofline materials, scicomp SE worked examples: FMA chain 15.9x vs memcpy-class 3.2x at 16T).
14. Roofline framing for honesty: saxpy arithmetic intensity ~1/6 FLOP/byte (Cornell Virtual Workshop) puts every modern CPU in the bandwidth-bound region; Speedup ~= min(compute-scaling, bandwidth-scaling); teaching labs (Berkeley CS267 hw1 style) grade on achieved GB/s as % of measured STREAM peak, where 50–85% is a realistic good result.
15. Windows/hardware specifics: std::thread::available_parallelism() on Windows respects the process affinity mask and job-object CPU-rate limits (uses GetActiveProcessorCount(ALL_PROCESSOR_GROUPS) + GetProcessAffinityMask; rust PR #97925); returns logical CPUs (32 for a 16c/32t Ryzen). hardware_concurrency() ignores affinity and is group-limited on >64-LP systems (processor groups only matter on Threadripper/Xeon-W class parts). No NUMA concerns on single-socket AM5/LGA1700 desktops — UMA, ignore first-touch tuning (ServeTheHome/Intel single-socket guidance).
16. Hybrid P/E cores (Intel 12th-gen+) are a real hazard for static-partitioned parallel-for: with equal chunks and a join barrier, total time = slowest E-core thread. Documented cases: llama.cpp #842 (13900K: 24 threads gave ~50% utilization; ~10 threads pinned to 8 P-cores was ~10% faster overall), llama.cpp discussion #572 (12700F: 2–3x slower with E-cores active), Intel oneMKL officially recommends P-cores-only (KMP_HW_SUBSET=1p). Windows 11 offers soft hints SetThreadSelectedCores/CPU Sets (learn.microsoft.com 'Thread Scheduling on Hybrid Architectures'); Rust std exposes no affinity API (rust-lang/rust#91009 open) — use core_affinity crate or windows-rs if desired. AMD Zen desktop has no E-cores; SMT siblings share FPU ports so physical-core-count threads often beat logical-CPU count for FP-heavy bodies.
17. Rust std parking on Windows is backed by WaitOnAddress/WakeByAddressSingle (library/std/src/sys/pal/windows/thread_parking.rs), i.e. futex-equivalent; condvar wake latency on Windows measured 6–30 us (alexanderhoughton.co.uk benchmarks) — hence spin-first. Lost-wakeup requires setting the sleeper flag atomically AFTER re-checking for work and unparking only if the flag was set (rayon src/sleep.rs, Mara Bos 'Rust Atomics and Locks', blog.m-ou.se/condvars).
18. Cranelift (latest umbrella/cranelift-jit 0.135.0, published 2026-08-20, MSRV 1.86): JITModule/Module/Context are NOT Sync — compile and finalize_definitions on one thread, but finalized function pointers are plain executable memory safe to call concurrently from all pool workers (docs.rs/cranelift-jit, bytecodealliance FAQ, issue #731). Pointers in Cranelift IR are i64 (pointer_type()); Win64 ABI passes the first four integer/pointer args in RCX,RDX,R8,R9 with mandatory caller-allocated 32-byte shadow space (Cranelift call conv windows_fastcall handles this in abi_impl.rs) — so a host fn helix_parallel_for(i64 start, i64 end, i64 body_fn_ptr, i64 ctx, i64 nthreads) declared with pointer_type()/i64 params links cleanly against JIT'd callers.
19. Work-stealing deques (Chase-Lev, Le et al. PPoPP'13) are overkill for a flat parallel_for: the Apache Arrow 'Work Stealing Thread Pool Investigation' concluded a simple mutex/counter design matched Chase-Lev macro-benefits on non-NUMA hardware ('not worth it'; complexity forces raw pointers and TSAN false positives). Pedagogical ladder: global atomic counter -> per-worker deques -> lock-free Chase-Lev.

## Recommendations

1. Ship both runtimes and benchmark them against each other as a course exercise: Stage A = std::thread::scope(|s| ...) spawning nthreads-1 workers per call with static chunks (~100 LOC, zero unsafe beyond the raw body-fn-pointer call); Stage B = persistent pool (Vec of workers created once, Condvar-or-park based, bounded spin of a few hundred spin_loop() iterations then park). Students then measure the fixed overhead delta (~100 us -> ~2 us per region) — this is the single most instructive graph in the project.
2. Default scheduler = static contiguous equal chunks using the libgomp formula (q = n/P, t = n%P, first t threads get q+1), and ALIGN chunk boundaries to 64-byte multiples so adjacent threads never straddle a cache line in the output array. Expose schedule(static|guided|dynamic,k) as a language/runtime knob so students can reproduce the 1.5–3x dynamic-vs-static gap themselves.
3. Implement dynamic/guided as ONE relaxed-ordering AtomicI64 next-index fetched via compare_exchange/fetch_add with chunk = max(min_chunk, remaining/nthreads) — 15 lines, mirrors libgomp, no Chase-Lev deque. Pad the counter in its own CachePadded cell. Do not attempt per-thread deques for v1.
4. Reduction lowering: allocate a Vec of #[repr(align(128))] cells (or crossbeam_utils::CachePadded<T>, crossbeam-utils 0.8.22) holding per-thread accumulators initialized to the monoid identity (+/-: 0, *: 1, min: +INF/type MAX, max: -INF/type MIN); the JIT body writes its thread's slot; after join the coordinator folds slots in a trivial serial loop (O(P) <= 32 ops, unmeasurable). Never emit atomic RMW into the hot loop; reserve atomics only as a 'what not to do' demo.
5. Document (and test with tolerance) that float + and * reduction results are order-dependent and may differ run-to-run from the sequential baseline — quote the OpenMP spec's 'order of combination is unspecified' clause; integer reductions are exact. Make tests compare with relative epsilon or sort-free exact match only for i32/i64.
6. Cost-model gate mirroring OpenMP's if clause: run serial when n < max(K_MIN, GRAIN * nthreads) with GRAIN ~= 1024 for light bodies (or estimate work_us = n * per_iter_cost and require >= ~50–100 us), and cap nthreads at std::thread::available_parallelism(). Provide env override (HELIX_NTHREADS, HELIX_SCHEDULE) for scaling-study labs. Print the decision when a verbose flag is set — great for grading.
7. Benchmark narrative template for the report: bytes_moved = n * sizeof(T) * (loads + stores); achieved_GBps = bytes / time; plot achieved_GBps alongside speedup-vs-serial and annotate the machine's measured STREAM-triad peak. State up front: 'at 50M f32 elements saxpy moves 600 MB; our dual-channel DDR5 tops out near X GB/s, so the theoretical maximum speedup from Y GB/s single-threaded is ~Y/X — we measured Z.' Expect ~4–6x @ 8–16T for saxpy, 12–15x for cache-resident compute-bound kernels.
8. Pool hygiene details that will otherwise bite: (1) wake workers by flipping state BEFORE enqueueing and unpark conditionally (lost-wakeup fence); (2) workers re-check for work after being woken (spurious wakeups are legal per std::thread::park docs); (3) warm the pool with one dummy parallel region before timing — the first region pays lazy thread creation; (4) bound the idle spin (few us, crossbeam Backoff pattern) then park so serial phases aren't starved by spinning workers; (5) take median of >= 5 timed reps.
9. For the Cranelift side: declare helix_parallel_for with signature (pointer_type, pointer_type, pointer_type, pointer_type, pointer_type)->() or i64 params under the windows_fastcall call conv, register it as a JIT symbol; compile/finalize the module once on the main thread, then let every pool worker call the body_fn_ptr(ctx, i, end) directly — finalized JIT code is fully re-entrant. Ensure generated index arithmetic sext's i32->i64 before address computation (50M f64 = 400 MB exceeds what sloppy i32 offset math tolerates in edge cases).
10. Add one optional lab: detect hybrid topology (GetLogicalProcessorInformationEx EfficiencyClass via windows crate) or simply rerun with HELIX_NTHREADS = 8 vs 32 on an Intel hybrid machine, showing E-core stragglers capping speedup at the slowest thread — and optionally pin with SetThreadAffinityMask/core_affinity to demonstrate recovery.

## Pitfalls

1. Spawn-per-call on Windows is 50–100 us PER THREAD (CreateThread + CRT/TLS init + stack commit); a 16-thread parallel-for costs ~1–2 ms fixed. Any loop shorter than ~5 ms loses to the serial version. Fine for your 50M-element demos (~9 ms), fatal for small-n tests.
2. Naive shared accumulator: an unpadded array of f64/u64 partials (adjacent elements on one line) or one atomic add per iteration will show 2–10x and 10–50x slowdowns respectively at higher thread counts — these are the two most likely ways students 'discover' negative scaling. Both are preventable with align(128) cells + post-join fold.
3. Atomic counter with chunk=1 destroys memory-bound throughput twice over: cacheline ping-pong on the counter AND broken per-thread prefetch streams (each grab lands on a different core). Always clamp chunk >= 8–64, prefer remaining/P guided decay for uniform loops.
4. E-core straggler effect on Intel hybrid chips: static equal partitions + join means wall time = slowest E-core thread; documented 2–3x regressions versus P-core-only configs (llama.cpp #842/#572, Intel MKL guidance). AMD Zen desktop unaffected; SMT siblings contend for FPU ports so logical-CPU-count threads can underperform physical-core-count for FP bodies.
5. FP reduction nondeterminism: per-thread partial combine order varies run-to-run; exact-equality unit tests against the sequential result will intermittently fail for float +/*. Also '-' reduction lowers to '+ negate' with the same caveat.
6. Lost-wakeup races in a hand-rolled park pool: if the sleeper flag is set AFTER checking the queue, or unpark is skipped because 'it can't be sleeping yet', workers hang forever. Follow the rayon/std futex discipline (flag set after re-check; unpark only if flag was set; always re-check after waking).
7. Spinning forever between regions starves the main thread and other processes during serial phases (the problem KMP_BLOCKTIME exists to manage); conversely pure condvar sleep costs 6–30 us wake on Windows and can exceed the whole region for small loops. Bound the spin.
8. First timed parallel region includes lazy thread creation and cold TLB/pages; benchmarks will understate steady-state speedup unless the pool is pre-warmed and arrays are touched once before timing.
9. JITModule is !Sync: calling define_function/finalize_definitions while workers execute previously finalized code paths is fine, but compiling new functions concurrently from pool threads is not — funnel all compilation through the main thread or a mutex.
10. Chunk boundaries misaligned to cache lines put two threads' last/first elements on one line of the OUTPUT array — false sharing even with perfect scheduling; round chunk sizes up to 16 f32 / 8 f64 elements.
11. available_parallelism() can return a value shrunk by process affinity masks, job objects, Process Lasso/efficiency-mode tools, or WSL/sandbox environments — don't hard-assert it equals 32; also processor groups (>64 LPs, Threadripper PRO) can hide CPUs from older APIs.
12. Ignoring the memory ceiling in the write-up invites overclaiming: claiming 'near-linear 16x' for saxpy is falsifiable by any grader with a calculator (600 MB / 8.6 ms floor). Report achieved GB/s vs measured STREAM peak, and explain the plateau as bandwidth saturation, not a bug.
13. i32 iteration/index arithmetic in generated code: 50M fits i32, but intermediate byte offsets (i * size_of::<T>()) overflow i32 for f64 arrays past ~268M elements and generally after promotion mistakes — sext to i64 before address math.
