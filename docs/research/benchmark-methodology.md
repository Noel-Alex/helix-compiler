# Research digest: benchmark methodology

_Verified August 2026 via parallel web research. Raw JSON: docs/research/raw/_

## Summary

A defensible college-report methodology for HELIX Lite is a small hand-rolled interleaved-round harness using std::time::Instant (QPC-backed on Windows, 10 MHz / 100 ns tick), with 3+ untimed warmup rounds that absorb JIT first-call compilation (reported separately), adaptive repetition to make each sample 100-250 ms, median-of-15-plus-CV reporting, and A-B-C interleaving of interpreter/native-sequential/native-parallel to defeat thermal drift. Criterion (0.7.x) can drive FFI calls via iter_custom but its nanosecond-scale statistical machinery and per-benchmark reports are a poor fit for producing cross-variant speedup tables, so it should be at most a dev-dependency sanity check. Cheats are prevented by calling the JITed kernel through a raw function pointer, consuming results via a printed checksum shared by all three execution modes, pre-allocating/touching buffers once, padding per-thread reduction accumulators to 64-byte cache lines, and choosing (and disclosing) a cache regime. Presentation should pair a speedup table with a parallel-efficiency column, an Amdahl serial-fraction note, a self-measured STREAM-triad bandwidth ceiling for memory-bound kernels, absolute ns/elem numbers, and a hand-written-Rust anchor run so 100x+ interpreter gaps read as expected (literature range for tree-walkers on numeric loops: ~10-150x) rather than bogus.

## Key facts

1. Rust std::time::Instant on Windows is implemented over QueryPerformanceCounter (per official docs); QPC frequency on Windows 11 is typically 10,000,000 Hz => 100 ns per tick, monotonic, fixed at boot; Instant::now() call overhead is roughly 20-30 ns, so any timed region >= 1 ms makes timer resolution and overhead negligible (<0.01%).
2. quanta crate latest is 0.12.3 (crates.io): RDTSC-based Clock calibrated against QPC, with Upkeep background-recalibration thread; has a known long-run drift issue (metrics-rs/quanta #91). Only worth adding for sub-microsecond regions, which HELIX kernel benchmarks are not.
3. Criterion latest line is 0.7.x (0.7.0 mid-2025, maintenance mode, MSRV 1.80+). Bencher::iter_custom lets you wrap FFI/JIT-pointer calls with your own clock, and std::hint::black_box (stable since Rust 1.66, best-effort identity-with-pessimism) prevents constant-folding of inputs; but criterion's output (bootstrap CIs per single benchmark, Tukey outlier classes, HTML plots) does not yield the interpreter-vs-native comparison tables the report needs.
4. Kalibera & Jones, 'Rigorous Benchmarking in Reasonable Time' (ISMM 2013) is the standard citation: discard warmup, ~30 repetitions gives tight confidence intervals, prefer Level-3 designs (multiple process invocations) when JIT/GC state matters, report CIs of ratios/differences rather than eyeballing overlapping intervals.
5. Windows noise controls: SetPriorityClass(HIGH_PRIORITY_CLASS or safer ABOVE_NORMAL_PRIORITY_CLASS) via windows-sys; High Performance power plan (powercfg /setactive SCHEME_MIN) prevents core parking/frequency-scaling artifacts; timeBeginPeriod became per-process in Windows 10 2004, so other processes' timer requests still perturb scheduling; Sleep(1) granularity is ~15.6 ms by default.
6. False sharing: pad per-thread accumulators to one 64-byte cache line ([repr(align(64))] wrapper) and give each thread a contiguous block chunk, not a stride-N slice; unpadded adjacent counters can scale negatively with thread count (Preshing; TU Delft concurrency notes).
7. Bandwidth ceilings: dual-channel DDR5 desktops reach ~65-80 GB/s in STREAM Triad vs ~76.8-96 GB/s theoretical (70-85% rule); single-thread streams often only 20-35 GB/s, so multi-core memory-bound speedup saturates well below core count. Measure achievable BW with your own triad-shaped HELIX/Rust kernel instead of quoting the spec sheet.
8. Arithmetic intensities (Williams-Waterman-Patterson roofline): saxpy f64 moves 24 B/elem for 2 FLOP (AI ~0.08-0.11), scale 16 B/elem, dot product 16 B/elem for 2 FLOP (AI ~0.125) - all deeply DRAM-bound; naive matmul is low-AI until blocked, and i-k-j ordering beats naive i-j-k by ~3-5x from stride-1 access alone.
9. Distance-1 recurrence x[i] = a*x[i-1] + b is a first-order linear recurrence with a distance-1 flow dependence through the array (GCD test: gcd(1,1)=1 divides everything); it is NOT a reduction because intermediate stored values are needed, so auto-parallelizers must reject it - the canonical negative test for HELIX's dependence analysis.
10. Tree-walking interpreters on numeric loops are commonly 10-150x slower than compiled code (community consensus; Crafting Interpreters shows jlox ~an order of magnitude slower than clox alone), so a 100x+ HELIX interpreter-to-native gap is within published expectations provided per-op absolute numbers and a Rust-reference anchor are shown.
11. Environment capture: sysinfo 0.37.x gives CPU brand/clocks, total RAM, OS name/version/kernel programmatically in-process; hyperfine's JSON schema (command, mean/stddev/median/min/max plus full raw 'times' array) is a good model for HELIX result files; charts are best generated offline from saved JSON via a small Python/matplotlib script.
12. Cranelift JIT hygiene: cranelift-jit's own jit-minimal example establishes the pattern - obtain get_finalized_function pointer, transmute, call, assert/consume the result; enable set_disasm(true) (+ capstone) to inspect emitted code and prove loads/stores were not elided.
13. Parallel FP reductions change summation order, so parallel results cannot be bit-compared to sequential ones; min/max reductions are order-independent and bit-exact, and integer accumulation is exact - use these for strict checksum validation and relative-tolerance checks (e.g., |diff| <= 1e-9*|sum|) for FP sums.

## Recommendations

1. Build a hand-rolled ~150-line bench harness as examples/bench.rs instead of adopting criterion as the primary tool: it interleaves variants, adapts rep counts, writes JSON, and prints the report tables directly. Keep criterion 0.7 (dev-dependency, iter_custom + std::hint::black_box) only as an optional micro-region sanity check if desired.
2. Harness protocol per (kernel, N, variant): (1) untimed warmup round 1 triggers JIT compile - time the compile separately and report it as its own column; (2) two more untimed warmup rounds stabilize caches/branch predictors/page tables; (3) take k=15 samples, each timing R inner reps chosen so the sample lasts 100-250 ms (pick R from a pilot run per variant - the interpreter needs far fewer reps than native); (4) report median, min, and CV = stddev/mean, and rerun automatically if CV > 5%.
3. Interleave variants round-robin (interp, native-seq, native-par, interp, ...) rather than finishing one variant before starting the next; this defeats thermal drift and background-load drift. Fix the round order or randomize within rounds, and record which.
4. Run the whole suite under: HIGH (or ABOVE_NORMAL) priority via SetPriorityClass from windows-sys, High Performance power plan, AC power, Defender exclusions for the target dir, no browser open; pin nothing by default but optionally add a --pin mode using SetThreadAffinityMask and disclose it in the report.
5. Anti-cheat checklist baked into the harness: call the JITed kernel through a raw extern fn pointer (LLVM cannot hoist/DCE it); after timing, checksum every output array (sum of bits or FNV-1a) and print it; require all three execution modes to produce matching checksums (bit-exact for int/min/max kernels, tolerance-based for FP reductions); pre-allocate and touch all buffers once before any timing; keep data magnitudes in ~1..100 to avoid denormal penalties.
6. Pre-spawn the HELIX thread pool once at startup and barrier-sync each rep; include the barrier inside the timed region (honest) and additionally report a pure-compute number for one large kernel where sync cost is <1%, so readers can separate pool overhead from scaling limits. Pad per-thread reduction partials to 64 bytes and chunk iterations as contiguous blocks.
7. Choose the cache regime explicitly per kernel: medium sizes (N=2^20 f64, ~8-16 MB working sets) sit near LLC for steady-state runs, and large sizes (N=2^24-2^26, hundreds of MB) force DRM-bound behavior; state array footprint vs LLC size in every table caption. Skip user-space cache flushing (clflush games) - undocumented and unnecessary at these sizes.
8. Add a self-measured bandwidth ceiling: implement a STREAM-triad-equivalent kernel in HELIX (a[i]=b[i]+s*c[i]) plus the same in plain Rust, derive achievable GB/s, then report HELIX parallel saxpy/dot GB/s as % of that ceiling next to the speedup column - this converts 'we got 22x' into 'we reach 82% of the machine's usable bandwidth'.
9. Report format per kernel: columns = kernel, N, variant, median time, ns/elem, speedup vs interpreter, speedup vs native-seq, parallel efficiency E_p=S_p/p, ideal speedup p, CV%. Sweep p in {1,2,4,8,16,24,32}. Follow Hoefler-style rules: state the baseline explicitly, always show absolute performance alongside speedups, avoid log-log axes that hide inefficiency.
10. Frame the interpreter gap credibly: (a) lead with ns/elem per variant; (b) cite the 10-150x tree-walker range (Crafting Interpreters jlox/clox, community measurements); (c) include a hand-written Rust release-build twin of each kernel and show HELIX-native lands within ~1.2-2x of it, which validates the Cranelift pipeline and makes the 100x+ ratio arithmetically inevitable; (d) separate kernel-only from end-to-end (parse+compile+run) timings and label which is shown.
11. Amdahl note in the report: S_max = 1/f_serial; estimate each kernel's serial fraction (JIT dispatch, final combine, barriers) from the p=1 vs asymptotic times and show the fitted Amdahl curve overlaid on measured points; expect efficiency to drop past the physical-core count since 32 logical CPUs likely means 16 cores + SMT - present efficiency against both counts.
12. Reproducibility bundle: meta JSON written once per campaign (CPU brand/cores via sysinfo 0.37, total RAM, OS build, rustc --version --verbose string, cranelift/wasmtime versions from Cargo.lock, power plan, date, RNG seed, git rev); one results JSON per run modeled on hyperfine's schema including the raw per-sample times array so medians can be recomputed offline; deterministic seeded input generators shared by all variants; commit all JSONs to the repo.
13. Generate figures offline from saved JSON with a short Python matplotlib script (speedup-vs-threads lines per kernel, efficiency curves, roofline overlay with the measured triad ceiling, box/violin of sample distributions); save SVG or 300-dpi PNG. Keeping plotting out of the Rust binary keeps the harness dependency-free (serde_json is the only extra runtime dep).
14. Kernel suite with sizes tuned for a 16C/32T desktop: saxpy y+=a*x (f64, N=2^16 and N=2^24); scale y=s*x (N=2^24); dot-product reduction + (i64 accumulator option for exactness, f64 for realism; N=2^26); min/max reduction (N=2^26, bit-exact validation); distance-1 recurrence x[i]=a*x[i-1]+b (N=2^24, must be REJECTED - log the dependence-analysis verdict and run sequential); 5-point Jacobi stencil + 2D init on 4096x4096 f64 interior (134 MB/array, DRAM-bound, rows independent); matmul C=A*B at 512x512 and 768x768 f64 with outer i-loop parallel and innermost k as a recognized +-reduction (ikj ordering optional).
15. Include deliberate negative/small cases in the demo: N=2^12-2^16 parallel runs where threading does not pay (efficiency < 1) presented honestly, and the rejected recurrence - examiners reward a compiler that refuses unsound parallelizations and authors who admit overhead regimes.

## Pitfalls

1. FP reduction parallelization reorders additions, so parallel checksums will not match sequential ones bit-for-bit; validating with == will fail spuriously. Use min/max or integer kernels for strict equality and relative tolerance for FP sums, and document the reassociation.
2. The first call to a freshly compiled HELIX function includes Cranelift codegen; folding it into steady-state timings corrupts small-N numbers. Time compilation separately and exclude it from kernel samples (warmup absorbs it).
3. 32 logical CPUs are probably 16 physical cores + SMT: expecting linear speedup to 32 invites a bogus-looking efficiency collapse around p>16. Present efficiency vs both logical and physical counts.
4. Windows Balanced power plan parks cores and varies boost clocks, producing multimodal timings that no amount of averaging fixes; likewise another process raising/lowering timer resolution changes scheduler churn (pre-Win10-2004 globally, per-process now). Control power plan and background state, and interleave variants so drift hits all variants equally.
5. Instant/QPC granularity is ~100 ns and Instant::now() costs tens of ns - harmless at >=1 ms regions but fatal if you try to time single sub-microsecond interpreter ops without batching many reps inside one timed region.
6. std::hint::black_box is best-effort and constant-folds expressions placed inside it (black_box(5*10) folds to black_box(50)); it protects host-side values, not the JITed body. The real protections are the raw fn-pointer call plus result checksumming - and remember HELIX's own DCE pass can delete stores of unused outputs, so the checksummed variable must be live in the HELIX source too.
7. Strided (round-robin) iteration assignment plus unpadded per-thread accumulators causes false sharing that can make parallel runs slower than serial; contiguous chunks and 64-byte-aligned accumulator padding are mandatory.
8. Denormal or huge-magnitude data can trigger 10-100x FP slowdowns on some paths and differ between interpreter and native arithmetic; initialize inputs to normal-range values.
9. Do not quote DDR spec-sheet bandwidth as the ceiling - desktops realize only ~70-85% of it in Triad, and single-threaded streams reach a fraction of the all-core figure; using spec-sheet numbers makes memory-bound speedup caps look like implementation failures.
10. Naive i-j-k matmul will be 10-100x below OpenBLAS; if included, scope the claim as 'HELIX vs its own interpreter/native modes', never vs vendor BLAS, or reviewers will flag the comparison as strawman.
11. Running all reps of one variant before another lets thermal/background drift bias whichever variant ran last; fixed-order blocking of variants is the most common student-methodology attack surface.
12. Log-log speedup plots hide severe inefficiency (Moreland/Oldfield); always tabulate efficiency numerically and keep axes linear where possible.
13. Adaptive rep-count differences between variants change how fixed overheads amortize; pick reps from a pilot run per variant and freeze them in the results metadata so the choice is auditable.
14. quanta's TSC calibration drifts from wall-clock over long sessions (issue #91) - irrelevant for short campaigns but another reason to just use Instant for millisecond-scale kernels.
15. Criterion's baseline-change detection assumes same-process reruns; using it across interpreter/native variants in one process conflates allocator/cache state, and its saved baselines live under target/ which gets cleaned - another reason it should not carry the report's headline numbers.
